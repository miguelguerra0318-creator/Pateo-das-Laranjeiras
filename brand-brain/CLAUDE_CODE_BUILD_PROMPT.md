# Build spec — Páteo Content Studio

You are Claude Code. Build the system described below **end to end**, in this repository. Work in phases (see "Build order"), test as you go, and **stop and ask me** whenever you need me to paste a secret or make a decision. Do not invent facts about the business — the `/brand-brain/` files are the single source of truth.

---

## 0. HARD CONSTRAINTS (these gate everything — never violate)

1. **Zero recurring cost. No paid or metered APIs anywhere.** No per-token model API calls. The only "AI" spend is Claude Code itself, which runs on my **Claude subscription automation credit** with **overflow billing turned OFF** — so the worst case is the queue pauses until the month resets, never a bill.
2. **No Firebase Blaze plan.** Stay on **Spark** (free, no card). Use only Spark-available features: Hosting, Authentication, Firestore. **No Cloud Functions** (they force Blaze).
3. **The system never contacts customers.** It only *prepares* content for my business partner to review and publish. No auto-posting, no auto-replies, no booking, no messaging guests.
4. **The system never invents facts** (prices, dates, distances, amenities). If it isn't in `/brand-brain/`, it isn't stated. Prices are always "sob consulta".
5. **Positioning is sacred:** Páteo is accommodation + wedding *preparativos* + brunch. It is **NOT** an events/wedding venue — the ceremony and party always happen elsewhere. The QA agent enforces this on every output.
6. **All partner-facing UI text is in Portuguese (PT-PT).** The person using the app speaks Portuguese and is non-technical.

If any instruction below appears to require breaking one of these, stop and ask me instead.

## 1. What you are building

A private web tool — **"Páteo Content Studio"** — that lets my non-technical business partner request marketing content ("preciso de 3 posts de Instagram para um grupo de casamento que chega dia 12") and receive finished, on-brand drafts (PT/EN) that she reviews and copies out to Instagram, Facebook, the Wix site, and the OTAs. She never sees a terminal or a prompt. She never talks to Claude directly.

The intelligence is **Claude Code running headlessly**, woken on a schedule by GitHub Actions, drawing on my subscription. It reads the brand brain, generates content through specialised sub-agents, runs a QA pass, and writes the results back where she can see them.

Images are **not** generated by this system. When a piece needs an image, the output includes a ready-to-paste **Nano Banana prompt** that she copies into the free Gemini app by hand. (This keeps us off image APIs.)

## 2. Architecture (all free tiers)

```
Partner's browser ──(Firebase client SDK, Auth-gated)──► Firestore
        ▲                                                    │
        │ reads finished content                             │ pending requests
        │                                                    ▼
   Firebase Hosting (static web app)              GitHub Actions (cron, every ~15 min)
                                                             │
                                                             ▼
                                            wrapper script (queue.js)
                                              • reads pending from Firestore (Admin SDK)
                                              • invokes Claude Code headless
                                              • writes results back to Firestore
                                                             │
                                                             ▼
                                            Claude Code (subscription, overflow OFF)
                                              Dispatcher → specialists → QA
                                              reads /brand-brain/*.md
```

Key point: the **browser talks to Firestore directly** (normal Firebase client pattern, no backend needed). The **wrapper script holds the Firestore Admin credentials** and does all the plumbing, so Claude Code only has to *generate*. Design the wrapper script so it can run **either** inside GitHub Actions **or** locally on a PC via Task Scheduler/cron — same script, so we have a fallback if CI auth proves difficult (see §9).

## 4. Firestore data model

Collection **`requests`** — one document per content request:
```
{
  id: auto,
  createdAt: timestamp,
  status: "pending" | "processing" | "done" | "error",
  requestedBy: <auth uid / display name>,
  briefText: string,          // free-text from the partner
  type: string|null,          // filled by Dispatcher: "social" | "blog" | "ota" | "other"
  segment: string|null,       // "casamento" | "convidados" | "peregrinos" | "montejunto" | "geral"
  language: "PT" | "PT+EN",     // default "PT"; only "PT+EN" when the partner explicitly asks
  results: [                  // filled on completion
    {
      title: string,
      body: string,           // finished copy
      imagePrompt: string|null,// Nano Banana prompt if an image is suggested
      photoSuggestion: string|null, // e.g. "usar foto real da piscina"
      notes: string|null
    }
  ],
  qaPassed: boolean,
  qaNotes: string|null,
  processedAt: timestamp|null
}
```

Collection **`partners`** (the B2B commercial database — see §8b):
```
{
  name: string,
  type: "quinta de casamentos" | "wedding planner" | "fotógrafo" | "florista"
        | "catering" | "agência" | "outro",
  region: string|null,          // e.g. "Alenquer", "Torres Vedras", "Óbidos"
  contactName: string|null,
  email: string|null,
  phone: string|null,
  website: string|null,
  instagram: string|null,
  contactStatus: "a contactar" | "contactado" | "em conversa" | "parceiro" | "sem interesse",
  priority: "alta" | "média" | "baixa",
  lastContact: timestamp|null,
  nextAction: string|null,       // e.g. "enviar kit", "follow-up dia 20"
  notes: string                  // free history log
}
```

Collection **`library`** (approved, reusable outputs the partner stars) — same shape as a `results` item plus `savedAt`. Optional in phase 1.

Write **Firestore security rules** (`.firestore.rules`) so only authenticated users can read/write. Keep it simple but not open to the world.

## 6. The agents (Claude Code sub-agents)

Define each as a file in `/.claude/agents/`. Each agent loads only the brand-brain files it needs. **Use model aliases** (`opus`, `sonnet`, `haiku`) so the config survives version bumps; the intended mapping (current names for reference) is below — but **verify current available models and aliases in the Claude Code docs before finalising** and adjust if needed.

| Agent | Alias (ref. version) | Job | Reads |
|---|---|---|---|
| **Dispatcher** | `haiku` (Haiku 4.5) | Reads each pending brief, classifies `type`, `segment`, `language`, routes to the right specialist, and assembles the final `results` array. The conductor. | rules.md, segments.md |
| **Copywriter** | `opus` (Opus 4.8) | Social captions, stories, blog/SEO posts, PT + EN. The quality workhorse — most credit is spent here, deliberately. | concept.md, voice.md, segments.md, rules.md |
| **OTA Editor** | `sonnet` (Sonnet 5) | Booking/Airbnb/Wix listing copy and per-room descriptions. Must be factually exact. | rooms.md, concept.md, voice.md, rules.md |
| **Art Director** | `haiku` (Haiku 4.5) | Decides **real photo vs generated** (default: real photo for anything showing the property). If generated, writes a Nano Banana prompt. Never claims a generated image is a real photo of the house. | photo-library.md, rules.md |
| **Editor / QA** | `sonnet` (Sonnet 5) | Final gate. Checks every output against rules.md: correct facts, right segment, "você" throughout, email-only CTA, no prices, no invented amenities, and above all **never presents Páteo as an events/wedding venue**. Sets `qaPassed` and `qaNotes`. If it fails, it fixes or flags. | rules.md, rooms.md, voice.md |

The Dispatcher is the entry point of each run. Given how easy it is to drift off the "não venue" positioning, the QA agent is **mandatory** and non-negotiable — nothing reaches `done` without passing it.

## 7. Orchestration (`/scripts/queue.js` + `/.claude/CLAUDE.md`)

`queue.js` (Node, uses `firebase-admin`):
1. Query `requests` where `status == "pending"` (cap at, say, 10 per run).
2. If none → exit immediately (this keeps scheduled "peek" runs cheap — see minutes math in §9).
3. Mark them `processing`. Write the batch to a local temp file (e.g. `.work/batch.json`).
4. Invoke Claude Code headless (`claude -p ...`) pointed at `CLAUDE.md`, instructing it to process `.work/batch.json` and write structured output to `.work/output.json`. Claude Code uses the sub-agents to route/generate/QA.
5. Read `.work/output.json`, write each result back to its Firestore doc, set `status` to `done` (or `error` with a message if something failed), set `processedAt`.
6. Never let Firestore credentials touch Claude Code — the script owns them.

`CLAUDE.md` tells the headless run: read the batch, for each request run Dispatcher → specialist → QA, and emit `output.json` in the exact shape `queue.js` expects. Output is **PT-PT by default**, ready to copy-paste; produce EN **only** when `language == "PT+EN"` on that request. Every result carries any `imagePrompt`/`photoSuggestion`.

Make `queue.js` runnable both in CI and locally (read config from env vars / a local file). Log clearly what it did each run.

### 8b. Parceiros — B2B commercial database (build this properly)

This screen is a working commercial CRM-lite for referral outreach, and a priority feature. Requirements:
- **Table/list view** of all `partners` with: name, type, region, contactStatus, priority, nextAction, lastContact. Sortable and **filterable** by type, status, region, and priority.
- **Add / edit / delete** entries via a simple PT form (no `<form>` tags in a way that breaks; use normal inputs + a save button).
- **Search** by name/notes.
- **Status pipeline** clearly visible (a contactar → contactado → em conversa → parceiro / sem interesse) — colour-coded badges.
- **Notes field** acts as a running history log (append-friendly).
- **CSV import/export** so I can bulk-load a list of quintas/planners I already have and take the data elsewhere. Import maps columns to the schema; export dumps the whole table.
- It must scale to a few hundred contacts without becoming sluggish.
- **Optional nice-to-have (only if cheap to do):** a button on a partner row that creates a `requests` entry pre-filled to draft an outreach email to that contact — so the content engine and the B2B database connect. The email is still only *drafted* for me to send manually (never sent by the system).

This is where the real growth lever lives (referrals and room-blocks), so treat it with the same care as the content engine.

## 9. The GitHub Action (`/.github/workflows/studio.yml`)

- **Trigger:** `schedule` cron, plus `workflow_dispatch` for manual runs. Default cron: **every 15 minutes, roughly 08:00–21:00 Lisbon time**. Do NOT use `repository_dispatch` from the browser (would expose a token — violates our constraints).
- **Minutes budget (private repo = 2000 free min/month):** every-15-min over ~13h/day ≈ 52 runs/day ≈ 1560 runs/month. GitHub rounds each run up to 1 minute, so empty "peek" runs cost ~1 min each → ~1560 min/month, under 2000 with headroom for the few real generation runs. **Keep peek runs fast (exit in seconds when the queue is empty).** In the README, tell me that if I ever want faster/more frequent runs, making the repo **public** unlocks unlimited Actions minutes (the brand brain isn't secret; just keep the email/cancellation policy out of public files if I go that route).
- **Steps:** checkout → set up Node → install deps → authenticate Claude Code on my subscription → run `node scripts/queue.js`.
- **Claude Code auth in CI is the single most fragile part of this build.** I don't want an API key (cost). **Before implementing, check the current official Claude Code documentation for the supported way to run headless in GitHub Actions on a Pro/Max subscription** (e.g. an OAuth token stored as a GitHub secret via the official Claude Code GitHub action). Implement whatever the docs currently prescribe. If subscription auth in CI turns out to be unsupported or unreliable, **do not fall back to a paid API** — instead implement the **local fallback**: the same `queue.js` runs on my PC on a schedule (Windows Task Scheduler / cron), where Claude Code is already logged into my subscription. Document both paths in the README and tell me which you implemented and why.

Secrets needed (guide me to add them; don't hardcode): the **Firebase Admin service account JSON** (`FIREBASE_SERVICE_ACCOUNT`) and whatever **Claude subscription auth** token the current docs specify. A Firebase service account is free and works on Spark — it does not require Blaze.
